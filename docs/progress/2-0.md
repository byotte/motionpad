# 2-0 움직임 계측 (코드 변경 없음)

REVIEW의 '계측 필요' 두 가지(플레이 화면 프레임 구성비, 눈 깜빡임 전체 재업로드 비용)를 쟀다.

## 도구
- `node tools/motion/frame_cost.js` (약 15분): 테스트 그림으로 실제 사용자 경로를 따라 프로젝트를 만들고(타원·마술봉 2·간략 범위지정), 장면을 하나씩 더하며 플레이 화면을 5초씩 잰다.
  - 장면: 그림만 → 영역 4개 자동 움직임(호흡·부드러운 반응·바람·꼬리 프리셋) → + 외곽까지 흔들기(꼬리) → + 눈 깜빡임 2개 → + 몸체 → + 터치 드래그
  - 그림 800×1000 / 같은 그림을 앱 최대 크기(1520×1900)로 키운 것. PC 화면, 폰 화면(CPU 1배·4배 느림). 화질 '고화질' 고정.
- `node tools/motion/frame_cost.js --blink`: 눈 깜빡임만. 깜빡임이 두 번 이상 들어가게 길게 잰다.
- 헤드리스 Chromium의 그래픽은 소프트웨어(SwiftShader)다. **JS 몫은 실기기 경향과 같지만 그래픽 몫은 실기기보다 훨씬 크다.** 같은 기계 전후 비교용.

## 결과
### 1. 물리·마스크는 원인이 아니다
모든 장면에서 물리 계산·마스크 갱신은 5초 동안 합계 0~7ms(프레임당 0.1ms 미만). 프레임 시간 대부분은 그래픽 처리(셰이더)다.

| 장면 (폰, 큰 그림, CPU 1배) | FPS | 프레임 평균 |
|---|---|---|
| 그림만 | 22.8 | 44ms |
| 영역 4개 자동 움직임 | 6.5 | 154ms |
| + 외곽까지 흔들기 | 6.3 | 160ms |
| + 눈 깜빡임 | 6.5 | 155ms |
| + 몸체 | 6.5 | 155ms |

영역을 켜면 FPS가 크게 떨어지는 건 소프트웨어 그래픽 탓이 커서, **실기기 수치가 필요하다**(아래 '부탁').

### 2. 눈 깜빡임 순간 끊김 — 확인
깜빡임 단계가 바뀔 때마다(한 번 깜빡일 때 약 30번) **그림 전체 크기**로 다시 합성하고 그래픽 쪽으로 통째로 다시 올린다. 눈은 그림의 1%도 안 되는데 매번 전체를 보낸다.

| 폰 화면 | 깜빡임 1번당 CPU(합성+업로드) | 끊긴 프레임 |
|---|---|---|
| 800×1000, CPU 1배 | 약 40ms | 없음 |
| 800×1000, CPU 4배 | 약 175ms | 없음 |
| 1520×1900, CPU 1배 | 약 125ms | 영역 있을 때 1번(283ms) |
| 1520×1900, CPU 4배 | 약 650ms (업로드가 85%) | **14번(평균 151ms)**, 영역 있을 때 7번(평균 474ms, 최대 517ms) |

비용이 그림 넓이에 비례한다(넓이 3.6배 → 업로드 3.8배). 눈 주변 사각형만 합성·업로드하면 그림 크기와 상관없이 작아진다.

### 3. FPS가 낮으면 움직임이 슬로모션이 된다 — 새로 찾음
앱 시간은 한 프레임에 최대 0.035초만 흐른다. 초당 28프레임 아래에서는 움직임·깜빡임 전체가 느려진다(20 FPS면 70% 속도, 6 FPS면 20% 속도). 물리 계산이 한 번에 크게 건너뛰다 튀는 걸 막으려는 장치인데, 느린 기기에서는 '끊김' 대신 '느려짐'으로 나타난다. 고치려면 물리를 작은 걸음으로 여러 번 나눠 계산하면 된다(물리 비용은 프레임당 0.1ms 미만이라 여유가 있다).

## 부탁: 실기기 FPS
폴드폰에서 영역 몇 개에 움직임을 켜고 플레이 화면 FPS(설정의 FPS 표시)를 알려 주면, 셰이더 최적화가 필요한지 판단할 수 있다.
